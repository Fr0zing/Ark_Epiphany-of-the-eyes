# Контекст проекта ARK Tracker Reborn

Этот файл предназначен для передачи проекта в новый чат или другой аккаунт. Перед любой работой сначала прочитай его, затем `README.md`, `REBORN.md` и актуальные настройки из `bin/Reborn/ui-settings.ini`.

## Что хочет пользователь

Пользователь развивает внешний ESP/радар для ARK: Survival Evolved (ASE). Основные требования:

- только чтение данных `ShooterGame.exe`;
- без DLL-инжекта, хуков и изменения памяти игры;
- минимально возможная задержка внешней отрисовки;
- красивый, понятный, нетехнический интерфейс на русском языке;
- overlay не должен блокировать мышь во время игры;
- интерактивное меню открывается отдельно и должно нормально принимать мышь;
- никаких функций aim/aimbot;
- изменения обычно нужно сразу реализовывать, собирать и проверять, не ограничиваясь описанием идеи.

Пользователь предпочитает короткое, прямое общение на русском. При изменениях интерфейса важны визуальная чистота и отсутствие большого количества перекрывающихся надписей.

## Текущее состояние

Рабочая production-сборка находится в `bin/Reborn`:

- `ArkTracker.Reborn.exe` — C#/.NET Framework x64 приложение и меню;
- `ArkOverlayNative.dll` — быстрый native Direct3D 11 + Direct2D + DirectComposition overlay;
- `tracker.ini` — сигнатуры и offsets ASE;
- `ui-settings.ini` — пользовательские настройки интерфейса и ESP;
- `arktracker.log` — диагностический лог, создаётся при работе.

Последняя Release-сборка и команда `ArkTracker.Reborn.exe --self-test` завершились успешно с кодом `0` 18 августа 2026 года.

## Как запускать

Основной запуск:

```text
Start-ARK-Reborn.cmd
```

Приложение может запросить UAC для read-only подключения к `ShooterGame.exe`.

Горячие клавиши:

- `Insert` или `F10` — открыть/закрыть меню;
- `F6` — общий ESP;
- `F7` — скелет;
- `F8` — имена;
- `F9` — здоровье;
- `F11` — только противники.

Когда меню скрыто, overlay использует click-through и не должен перехватывать мышь. Когда меню открыто, native overlay временно скрывается, а окно настроек становится интерактивным.

## Как собирать и проверять

Полная Release-сборка:

```powershell
.\build-reborn.ps1 -Configuration Release
```

Только C# без пересборки native DLL:

```powershell
.\build-reborn.ps1 -Configuration Release -SkipNative
```

Только native overlay:

```powershell
.\build-native.ps1 -Configuration Release
```

Самопроверка:

```powershell
.\bin\Reborn\ArkTracker.Reborn.exe --self-test
```

Перед полной сборкой нужно проверить процесс `ArkTracker.Reborn`. Запущенное приложение блокирует production DLL/EXE. Останавливать следует только процесс с точным именем `ArkTracker.Reborn`; `ShooterGame.exe` без необходимости не закрывать.

Перед возвращением нужно отдельно найти надёжную read-only цепочку до экипировки удалённого персонажа, проверить все пять слотов и текущую/максимальную прочность на нескольких других игроках. Быстрые слоты были удалены по просьбе пользователя. Не возвращать их без нового запроса.

### Союзные племена

19 августа 2026 года добавлено отдельное отношение `Ally`, не зависящее от старого режима «Выбранные племена».

На странице «Игроки» появился список «Союзные племена». Пользователь отмечает найденные племена вручную. Выбор сохраняется в `ui-settings.ini`:

```text
AllyTeams=123,456
AllyColor=49B8FF
```

Логика отношений:

1. Совпадает с `LocalTargetingTeam` → своё племя.
2. Команда находится в `AllyTeams` → союзник.
3. Команда выбрана в специальном режиме «Выбранные племена» → выбранная.
4. Остальные известные чужие команды → противники.

Союзное отношение применяется к игрокам, приручённым существам и постройкам одного `TargetingTeam`. В режиме «Только враги» союзные объекты скрываются. Native overlay использует отдельный `AllyColor`; союзники не попадают в `ThreatIndicator`, поскольку имеют relation `4`, а не `Enemy`. Защита от Ноглина также проверяет `AllyTeams` до срабатывания.

Автоматическое чтение игрового списка альянсов пока не реализовано: ручной выбор надёжнее, потому что наличие и репликация серверной структуры alliance ещё не проверены. Release-сборка и `--self-test` после изменения прошли с кодом `0`.

### Результаты проверки брони через память

18 августа 2026 года локальные PDB-данные текущей версии `ShooterGame.exe` были повторно проверены. Для экипировки найдена следующая read-only цепочка:

```text
APrimalCharacter / AShooterCharacter
  + 0xCE0  MyInventoryComponent -> UPrimalInventoryComponent*
UPrimalInventoryComponent
  + 0x128  EquippedItems -> TArray<UPrimalItem*>
```

Поля каждого `UPrimalItem`:

- `+0x172 MyEquipmentType` — тип экипировочного слота;
- `+0x328 DescriptiveNameBase` — читаемое название предмета (`FString`);
- `+0x238 ItemRating` — рейтинг предмета;
- `+0x298 ItemQualityIndex` — индекс качества;
- `+0x3D8 NewItemDurabilityOverride` — необязательное переопределение прочности, не считать его универсальным максимумом;
- `+0x558 ItemStatValues` — массив значений характеристик предмета;
- `+0x57C ItemDurability` — текущая прочность;
- `+0x580 MinItemDurability` — минимальная граница;
- `+0x5A0 ItemIcon` — указатель на игровую текстуру иконки.

В `UPrimalInventoryComponent` также найден сетевой флаг `bReceivingEquippedItems`, что подтверждает существование механизма получения клиентом экипированных предметов. Однако заполнение массива для удалённых игроков обязательно нужно подтвердить живой проверкой.

Главная ошибка старой реализации: нельзя считать первые пять элементов `EquippedItems` фиксированными слотами шлем/нагрудник/перчатки/штаны/ботинки. Массив может содержать `null`, оружие, скины и другие типы. Каждый предмет нужно классифицировать по `MyEquipmentType`, после чего выбирать только пять типов человеческой брони.

Текущая прочность читается напрямую из `ItemDurability`. Максимальная прочность не подтверждена как одно готовое поле: её нужно корректно получить из item stats/шаблона предмета и проверить на обычных, качественных и модовых предметах. Не использовать `NewItemDurabilityOverride` как максимум без проверки.

`ItemIcon` является указателем на UE-текстуру, которую нельзя безопасно и дёшево передать в обычный WinForms/native overlay как готовую картинку. Предпочтительный вариант UI — определить класс предмета и использовать локальный каталог PNG-иконок; неизвестным модовым предметам показывать нейтральную иконку и название.

Был выполнен отдельный диагностический проход с доступом только `PROCESS_QUERY_INFORMATION | PROCESS_VM_READ`: `GWorld` и `GNames` успешно разрешились, запись памяти не использовалась. В момент проверки snapshot содержал `0` объектов типа Player, поэтому репликацию `EquippedItems` другого игрока подтвердить не удалось.

Перед реализацией брони в новом чате необходимо:

1. Встать рядом с другим живым игроком, на котором надеты известные пять элементов брони.
2. Запустить read-only probe и записать для каждого игрока адрес inventory, размер `EquippedItems`, класс предмета, `MyEquipmentType`, `ItemDurability`, `ItemStatValues` и quality.
3. Снять/надеть один предмет и подтвердить, что массив обновился.
4. Повредить один предмет и подтвердить изменение текущей прочности.
5. Повторить на противнике/соплеменнике, спящем и мёртвом персонаже.
6. Только после успешной проверки возвращать UI из пяти слотов.

Итог проверки: броня других игроков выглядит технически реализуемой полностью через read-only память и без инжекта, но пока имеет статус `требует живой валидации`, а не `готово`.

### Визуал и производительность

- native GPU-overlay без инжекта;
- внешний быстрый цикл обновления, текущий `RefreshIntervalMs=8`;
- лимит FPS overlay;
- автоматическое уменьшение дальних подписей и линий;
- настраиваемые размер, обводка, прозрачность и фон текста;
- раздвижение перекрывающихся подписей;
- отдельные дистанции игроков, динозавров, построек и трупов;
- профили PvP, Пещеры, База и Минимальный;
- диагностические показатели задержки/FPS.

Абсолютно нулевую задержку без инжекта гарантировать нельзя: координаты читаются внешним polling-процессом, затем проецируются и рисуются отдельным окном. При оптимизации сохранять read-only архитектуру.

## Система построек

Последняя крупная доработка — категории построек. Она заменила один общий режим группировки.

Категории по умолчанию:

- `turrets` — «Турели»;
- `spam` — «Спам»;
- `crafting` — «Крафт-зона»;
- `storage` — «Хранилища»;
- `teleports` — «Телепорты»;
- `other` — «Остальное».

Для каждой категории на странице «Постройки» независимо выбираются:

- включена ли категория;
- режим «Каждая отдельно» или «Группировать»;
- показывать ли название;
- собственный цвет;
- правила состава через кнопку «Изменить».

### Логика классификации

Классификатор использует части `ActorRecord.ClassName` и `ActorRecord.DisplayName` без учёта регистра. Категории проверяются по порядку. Первое совпадение побеждает. Всё неизвестное попадает в `other`.

У каждой категории есть:

- `Includes` — ключевые слова для включения;
- `Excludes` — ключевые слова, запрещающие попадание в эту категорию.

Например:

- `turret`, `autoturret`, `plantx` → «Турели»;
- `foundation`, `pillar`, `barricade` → «Спам»;
- `fabricator`, `forge`, `replicator`, `smithy` → «Крафт-зона»;
- `storage`, `vault`, `dedicated`, `fridge`, `safe` → «Хранилища»;
- `teleport`, `teleporter`, `awesome_teleport` → «Телепорты».

Правила редактируются прямо из UI и сохраняются в `ui-settings.ini` как `StructureCategory.<id>.*`.

При группировке объединяются близкие объекты одной категории и одного `TargetingTeam`. Общая дистанция связи задаётся `StructureGroupingDistanceCm`. Для группы в overlay передаются центр группы и `ClusterCount`; название группы выглядит как `Категория ×N`. Без группировки каждая структура получает отдельную точку.

Точки и подписи имеют категорийный цвет, передаваемый через поле `VisualColor` структуры `ArkNativeActor`. Флаг `16` в `NativeActor.Flags` означает, что для структуры разрешена подпись.

Найденные внутренние классы отображаются в нижнем списке страницы построек вместе с назначенной категорией. Старый список выбранных классов всё ещё может дополнительно скрывать отдельные типы через `AllStructureClasses` и `StructureClasses`.

### Важно про актуальные настройки

Не перезаписывать `bin/Reborn/ui-settings.ini` значениями по умолчанию без просьбы пользователя. Пользователь уже менял режимы и цвета категорий. Всегда загружать и сохранять актуальный файл.

Текущее ограничение `MaxLabels=300` относится и к точкам. Если без группировки на очень большой базе отображается не всё, сначала проверить этот лимит. Простое безлимитное увеличение может повысить задержку, потому что каждый native actor содержит строки и массив костей; оптимальнее в будущем сделать отдельный компактный ABI-массив для structure points.

## Текущие технические ограничения и осторожность

- Offsets и сигнатура `GWorld` зависят от версии ASE и могут потребовать обновления в `tracker.ini`.
- Не добавлять запись памяти, инжект, обход античита или вмешательство в игру.
- Не запускать ASE через BattlEye при использовании локального диагностического режима проекта; текущая архитектура рассчитана на локальную/частную среду.
- Не удалять пользовательские настройки и не использовать destructive Git/filesystem-команды.
- В папке может не быть `.git`; сначала проверять, прежде чем рассчитывать на Git для отката.
- При правках native ABI всегда выполнять полную сборку и `--self-test`.
- В native сборке присутствуют известные предупреждения C4458 о затенении имён; они не блокируют сборку.

## Ближайшие разумные улучшения

Реализовывать только после запроса или если они непосредственно нужны для текущей задачи:

1. Прямое назначение конкретного найденного класса в категорию через выпадающий список, вместо копирования имени в Includes/Excludes.
2. Индивидуальная дистанция группировки для каждой категории.
3. Отдельные лимиты для текстовых подписей и дешёвых structure points.
4. Компактный native ABI для тысяч точек построек, чтобы не маршалить строки и скелет на каждую структуру.
5. Визуальная легенда цветов категорий на мини-радаре.

## План дальнейшего развития без инжекта

Все предложения ниже рассчитаны на текущую архитектуру: отдельная внешняя программа, только read-only чтение памяти `ShooterGame.exe`, без DLL-инжекта, хуков и записи в память игры. Это список идей и приоритетов, а не перечень уже готовых функций.

### 1. Динозавры

- имя, вид и уровень;
- приручённый или дикий;
- племя владельца;
- здоровье и торпор;
- пол, агрессивность и текущее состояние;
- отдельные цвета и дистанции;
- фильтры по виду и минимальному уровню;
- скрытие спящих, мёртвых или неинтересных существ.

### 2. Турели

- тип турели;
- включена ли она и получает ли питание;
- количество патронов, если оно реплицируется клиенту;
- режим наведения;
- приблизительная зона действия;
- скрытие пустых и выключенных турелей;
- разные цвета для обычных, тяжёлых, Tek-турелей и Plant X;
- предупреждение при входе в опасную область.

### 3. Предметы мира

- рюкзаки и трупы;
- выпавшие предметы;
- supply crates и другие контейнеры мира;
- дистанция и оставшееся время существования, если оно доступно;
- фильтры по качеству и типу;
- скрытие малоценных предметов.

### 4. Контейнеры и оборудование

- сейфы, холодильники и dedicated storage;
- forge, fabricator, replicator и grinder;
- обычные и Tek-генераторы;
- телепорты и передатчики;
- владелец, племя, здоровье и наличие питания.

Содержимое чужого закрытого контейнера может не передаваться сервером клиенту. Перед реализацией содержимого необходимо проверить, присутствуют ли данные в памяти до открытия контейнера.

### 5. Броня игроков

После живой проверки найденной цепочки `MyInventoryComponent -> EquippedItems` можно вернуть:

- пять настоящих слотов человеческой брони;
- название и качество каждого предмета;
- текущую прочность;
- цветовое обозначение состояния;
- локальные картинки предметов с универсальной иконкой для неизвестных модовых вещей.

Эта функция по-прежнему имеет статус `требует живой валидации на другом игроке`.

### 6. Умное отображение построек

- прямое назначение найденного класса в категорию через выпадающий список;
- индивидуальная дистанция группировки каждой категории;
- отдельная дистанция показа названий: вдали остаются только точки или иконки;
- максимальное число подписей для каждой категории;
- приоритет важных объектов, особенно турелей и телепортов;
- объединение близких подписей в одну компактную карточку;
- независимые режимы `точки`, `иконки` и `названия`;
- пользовательские наборы категорий и правил.

### 7. Информационная карточка выбранной цели

Вместо большого количества текста рядом с каждым объектом можно показывать одну компактную карточку выбранной цели:

- имя и племя;
- здоровье;
- оружие;
- дистанция;
- состояние персонажа;
- броня после успешной проверки её чтения.

Выбор цели должен быть только визуальным и не должен двигать мышь или прицел.

### 8. Мини-радар и предупреждения

- круговой радар вокруг локального персонажа;
- направление камеры;
- отдельные обозначения противников, своих, динозавров и турелей;
- предупреждение о приближении противника;
- счётчик противников в выбранном радиусе;
- стрелки на объекты за пределами экрана;
- настраиваемые радиусы предупреждений.

### 9. Снижение задержки и нагрузки

Приоритетные технические улучшения:

- разнести чтение памяти, построение snapshot и отрисовку по отдельным потокам;
- использовать двойной или тройной буфер snapshot без ожидания renderer-а;
- интерполировать положение между подтверждёнными чтениями;
- применять осторожное краткосрочное прогнозирование движущихся персонажей;
- использовать spatial hash/grid для группировки построек;
- передавать тысячи точек отдельным компактным native ABI-массивом;
- не передавать неизменившиеся строки, названия и скелеты каждый кадр;
- обновлять игроков часто, а неподвижные постройки значительно реже;
- выполнять screen-space, distance и category culling до marshaling в native DLL;
- отдельно измерять возраст snapshot, время чтения, подготовки и GPU-отрисовки.

Простое уменьшение `RefreshIntervalMs` ниже текущего значения может повысить нагрузку и сделать движение менее стабильным. Сначала следует профилировать этапы и убрать лишнюю работу каждого кадра.

### Ограничения внешнего read-only режима

Без инжекта нельзя надёжно реализовать настоящие chams через материалы игры, использовать игровой depth buffer, выполнять точную проверку видимости через геометрию или изменять механику оружия. Также невозможно прочитать данные, которые сервер вообще не реплицировал клиенту.

Не относятся к текущему плану: Silent Aim, AimLock, Auto Shoot, No Recoil, No Spread, Rapid Fire и другие функции, требующие воздействия на игру.

### Рекомендуемый порядок реализации

1. Профилирование и оптимизация задержки.
2. Расширенный ESP динозавров.
3. Турели и предупреждения об опасной зоне.
4. Живая проверка брони другого игрока и только затем возврат UI брони.
5. Информационная карточка выбранной цели.
6. Предметы мира, контейнеры и оборудование.
7. Мини-радар и дальнейшее улучшение системы построек.

## Концепция нового интерфейса и системы оповещений

Пользователь хочет не косметическую перестановку старых карточек, а заметно более удобную новую версию интерфейса. Переработку следует делать как единый центр управления, сохранив простой русский язык и моментальное применение настроек.

### Предлагаемая структура меню

Верхняя строка состояния:

- подключение к `ShooterGame.exe`;
- активен ли сканер и overlay;
- число обнаруженных противников;
- возраст snapshot и FPS отрисовки;
- крупная кнопка общего включения/выключения.

Левая навигация:

- «Главная»;
- «Игроки»;
- «Существа»;
- «Угрозы»;
- «Мир»;
- «Постройки»;
- «Оповещения»;
- «Горячие клавиши»;
- «Внешний вид»;
- «Производительность».

На левой панели также нужен компактный список того, что сейчас сканируется, с быстрыми переключателями и количеством найденных объектов. Настройки конкретной страницы показываются в центральной области. Справа на главной странице можно разместить живую ленту последних событий и карточку выбранной цели.

Вместо большого количества одинаковых технических карточек использовать логические группы, короткие описания, поиск настроек, понятные состояния переключателей, цветовой preview и кнопку восстановления только конкретного раздела.

### Настраиваемые горячие клавиши

Добавить отдельный редактор биндов:

- открыть/закрыть меню;
- общий ESP;
- включить/выключить сканирование;
- временно скрыть весь overlay;
- заглушить звуковые оповещения;
- игроки, существа, постройки и угрозы по отдельности;
- режим «только противники»;
- аварийное скрытие интерфейса.

Нужны обнаружение конфликтов, кнопка очистки бинда и отображение назначенной клавиши рядом с быстрым действием. Старые фиксированные F6–F11 сохранить как начальные значения, но не как жёстко зашитые клавиши.

### Событийные оповещения

Оповещения должны появляться только при новом событии или существенном изменении, а не повторяться каждый snapshot. Для каждого типа нужны индивидуальные дистанция, звук, цвет, время показа и cooldown.

Планируемые события:

- противник вошёл в выбранный радиус;
- противник приблизился до более опасного порога;
- обнаружен новый вражеский Ноглин;
- отслеживаемый игрок перешёл в состояние сна;
- обнаружен спящий игрок;
- игрок умер или исчез из наблюдаемой области;
- в радиусе появилась важная турель или другой выбранный объект.

Нужно хранить краткоживущее состояние обнаруженных акторов по адресу/устойчивому идентификатору, сравнивать два snapshot и подавлять дубли. Исчезновение из радиуса нельзя автоматически называть выходом из игры: актор мог выйти из сетевой релевантности или выгрузиться.

### Предупреждение о вражеском Ноглине

18 августа 2026 года базовая версия функции реализована:

- определить Noglin по имени класса и/или игровому имени;
- проверить `TargetingTeam`;
- считать угрозой только приручённого Ноглина чужого племени;
- диких и своих Ноглинов игнорировать;
- использовать настраиваемый радиус, например 50–100 метров;
- показать заметное экранное предупреждение, дистанцию и направление;
- воспроизвести отдельный звук с cooldown;
- при наличии антидота в локальных быстрых слотах определить номер нужного слота;
- автоматически нажать этот слот один раз на текущий вход угрозы;
- после выхода всех Ноглинов из радиуса повторно взвести защиту через настраиваемую задержку;
- после расходования последнего предмета показать «антидот использован · больше нет».

Классификацию Ноглина и его команды необходимо проверить вживую: у некоторых состояний контроля или модовых вариантов `TargetingTeam` и класс могут отличаться.

### Антидот в быстрых слотах

Используется read-only цепочка:

```text
LocalPawn
  + 0xCE0  MyInventoryComponent
Inventory
  + 0x138  ItemSlots -> TArray<UPrimalItem*>
Item
  + 0x10   UObject.Class
  + 0x328  DescriptiveNameBase
  + 0x5F8  ItemQuantity
```

Антидот распознаётся по классу и названию через настраиваемые ключевые слова `AntidoteKeywords`; начальные значения включают `curelow`, `antidote` и `lesser antidote`.

Текущее поведение:

- предупреждение «Вражеский Ноглин — 64 м»;
- отдельная страница меню «Угрозы»;
- переключатели защиты, автоматического применения и звука;
- радиус обнаружения и задержка повторного взведения;
- если антидот найден и ARK является активным окном, отправляется одна клавиша слота `1–0`;
- если окно ARK не активно или меню трекера открыто, применение ожидает безопасного состояния;
- если предмета нет, показывается крупная красная тревога;
- native overlay показывает дистанцию, слот, количество и результат применения.

Пользователь явно разрешил input automation для этой функции. Реализация не делает DLL-инжект и не записывает память игры, но проект теперь не является полностью пассивным при включённом `AutoUseAntidote`. Используется эмуляция клавиши через Win32 только после проверки foreground PID. В текущей реализации предполагаются стандартные игровые клавиши панели `1–0`; пользовательские переназначения ещё не поддерживаются.

Release-сборка и `--self-test` после добавления функции завершились с кодом `0`. Живая проверка всё ещё обязательна: положить Lesser Antidote в известный слот, проверить его внутренний класс/количество в UI и логе, затем проверить с вражеским приручённым Ноглином. До такой проверки функция имеет статус `реализована, требует проверки в ASE`, потому что точное наполнение `ItemSlots` и команда Ноглина могут отличаться на сервере или модовой сборке.

### Сон, offline-состояние, здоровье и торпор

Состояние сна уже читается через `APrimalCharacter.IsSleeping`, поэтому можно добавить:

- событие перехода игрока из бодрствующего состояния в сон;
- отдельный список спящих игроков;
- HP `текущее / максимальное`;
- торпор после поиска и живой проверки соответствующих полей;
- племя, дистанцию и время первого обнаружения;
- отдельные фильтры и цвета для спящих.

Состояние «не в игре» не следует считать равным `IsSleeping`. Надёжное определение online/offline требует найти и проверить сетевой признак или связь с controller/player state. До этого UI должен писать только подтверждённое состояние «спит», а не «вышел из игры».

## Реализованный этап умных построек и низкой задержки

19 августа 2026 года реализован следующий этап ранее сохранённого плана:

- у каждой категории построек появились собственная дистанция группировки, дальность текста, лимит подписей и внутренний приоритет;
- в списке найденных классов можно выбрать класс и назначить его в конкретную группу без ручного копирования ключевого слова;
- точные назначения классов и новые параметры категорий сохраняются в `ui-settings.ini`;
- игроки/существа и structure points используют разные бюджеты, поэтому тысячи фундаментов больше не вытесняют игроков из overlay;
- постройки без текста передаются новым компактным ABI `ArkNativeStructurePoint`; тяжёлый `ArkNativeActor` остаётся только для игроков и подписанных объектов;
- добавлен третий фоновый контур: позиции уже найденных игроков читаются по сохранённым RootComponent каждые 4–12 мс, не ожидая полного обхода Levels/Actors;
- при быстром обновлении корня старый скелет сдвигается на тот же мировой delta и не оставляет подпись позади персонажа;
- добавлена настраиваемая компенсация движения 0–50 мс по прочитанной скорости; после живой проверки значение по умолчанию возвращено к 0 мс, чтобы она не влияла на базовую плавность;
- диагностика отдельно показывает длительность полного обхода мира и быстрого чтения позиций;
- события дополнены двумя радиусами приближения противника, обнаружением новой чужой турели и общим cooldown.

Нативная DLL и C# EXE после изменения собраны вместе, новый compact ABI и переходы событий покрыты `--self-test`. Сначала следует проверять базовую плавность с компенсацией 0 мс; только при стабильном движении и постоянном отставании пробовать 8–12 мс.

После первой живой проверки обнаружен и исправлен источник периодического рывка всего player ESP. Полный обход мира занимал около 31 мс и после быстрого обновления позиции мог снова записать в native overlay более старые координаты. Из-за этого назад-вперёд двигались одновременно рамка, скелет, маркер и подпись. Теперь полный snapshot не отправляется в контур трансформаций, а `UpdateActors` при обновлении имён/HP/статусов сохраняет самую свежую позицию существующего игрока и совмещает с ней новый скелет. `--self-test` после исправления проходит.

Следующая диагностика показала примерно `Мир 40 мс`, `Позиции 0 мс`, `UI 26 мс`, `GPU 4,4 мс` и около `50 FPS`. Подробная подготовка акторов была вынесена с 16-мс WinForms timer в фоновый actor worker и ограничена частотой около 10 Гц; быстрые позиции и камера остаются независимыми. В диагностику добавлены отдельные значения `данные` и `камера`. Карточка увеличена, главное окно явно сделано растягиваемым и разворачиваемым.

Повторная живая диагностика показала `UI 0,2–0,3 мс`, `GPU 3,8 мс`, `Overlay 63 FPS`, но периодические `данные 22 мс`. Найден оставшийся источник рывка: C# удерживал один общий `nativeSync` во время маршалинга большого пакета акторов, поэтому камера и быстрые координаты раз в ~100 мс ждали до 22 мс. Native API уже потокобезопасен, поэтому вызовы переведены на общий read-lock, а эксклюзивный write-lock оставлен только для уничтожения handle. Быстрый контур RootComponent расширен с игроков на динозавров; медленный metadata refresh теперь сохраняет свежие координаты обоих видов динамических акторов. В карточку добавлена реальная частота циклов `мир / позиции / камера` в Гц. C# EXE и native DLL пересобраны, `--self-test` проходит.

После сообщения об оставшихся микрофризах сделан ещё один низкоуровневый этап. Нативный C++ renderer больше не использует неточный `sleep_for(1 ms)` и не помечает кадр показанным после потенциально отклонённого `Present(DO_NOT_WAIT)`. Swap chain переведён на `DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT`, очередь ограничена одним кадром, а render thread синхронизируется с точным сигналом compositor и работает с приоритетом `ABOVE_NORMAL`. Полный C# обход больше не читает скелеты: матрицы игроков вынесены в быстрый transform worker с периодом около 16 мс, а metadata refresh сохраняет последний свежий скелет. Быстрые слоты локального игрока читаются примерно раз в 8 полных снимков. Для многочисленных неподвижных построек добавлены короткие проверяемые кэши class/root/team и мировой позиции с периодической перепроверкой и очисткой исчезнувших адресов. Это уменьшает число `ReadProcessMemory` в полном обходе, не кэшируя позиции игроков и динозавров. Сборка и native self-test проходят.

На живой проверке после этого длительности упали до `мир 2 мс / данные 2 мс / позиции 0 мс / камера 0 мс`, но реальные счётчики всех трёх циклов одновременно показали только `64–66 Гц` на мониторе 144 Гц. Причина оказалась в системном шаге ожиданий Windows около 15,6 мс: `CancellationToken.WaitHandle.WaitOne(4)` фактически будил worker примерно 64 раза в секунду. На время работы `SnapshotPump` теперь сбалансированно вызываются `timeBeginPeriod(1)` / `timeEndPeriod(1)`. Карточка диагностики увеличена, а строка частот сокращена, чтобы GPU и Overlay FPS больше не обрезались. После запуска ожидаются существенно более высокие значения позиции/камеры; их нужно подтвердить живым скриншотом.

Живая проверка подтвердила результат: `мир 119 Гц`, `позиции 119 Гц`, `камера 219 Гц`. Позиции оставались на 119 Гц не из-за нагрузки, а потому что transform worker наследовал общий `RefreshIntervalMs=8`. Контур динамических RootComponent окончательно отделён от полного мира и зафиксирован на 4 мс; view и transform LongRunning threads получили `AboveNormal`. Ожидаемая частота позиций теперь около 200–220 Гц. Значение `Overlay 0 FPS` при открытом меню штатное: native ESP намеренно выключен на время интерактивного режима.

После внедрения waitable frame pacing проявился регресс повторного показа ESP: скрытый DirectComposition target мог перестать сигнализировать frame-latency object, а renderer ждал сигнал до отправки первого кадра после `Insert`. Получался цикл ожидания без ошибки в логе. В `SetEnabled(true)` теперь выставляется `forcePresent`; первый bootstrap-кадр после возврата окна отправляется без ожидания frame-latency сигнала, а после успешного `Present` renderer возвращается к обычному точному pacing. Native DLL пересобрана, self-test проходит.

Следующая проверка: при активном режиме Windows `3840x2160 @ 144 Гц` диагностика показала `мир 74 / позиции 215 / камера 215 Гц`, `GPU 1,6 мс`, но Overlay только `99 FPS`. Лимит ошибочно отсчитывался от конца предыдущего Render, поэтому к интервалу 6,94 мс добавлялось GPU-время и пропускались compositor slots. Отсчёт исправлен на start-to-start (`lastFrameStartedAt = renderStart`), то есть GPU-время теперь входит в бюджет кадра. Native DLL пересобрана, self-test проходит.

Добавлен фильтр диких динозавров. В ASE дикие существа используют малые служебные `TargetingTeam` (например 0/4/5/7), тогда как прирученные наследуют большой ID игрока/племени; текущая граница определения — `< 50000`. Настройка `ShowWildDinos` по умолчанию `False`, сохраняется в `ui-settings.ini` и доступна в разделе «Общее → Отображение» как «Показывать диких». Фильтр применяется не только к ESP, но и к быстрому transform worker, поэтому скрытые дикие существа не создают лишних высокочастотных RPM-чтений. Self-test проверяет скрытие wild и сохранение tamed.

19 августа 2026 года проведён полный аудит оставшихся микрофризов при показаниях `мир 117 / позиции 228 / камера 228 Гц`, `рендер 4 мс`, `Overlay 113 FPS` на мониторе 144 Гц. Найдены и исправлены несколько независимых причин:

- metadata `UpdateView` больше не отправляет устаревшую камеру из полного world-снимка поверх свежей камеры 228-Гц view worker;
- повторный `SetEnabled(true)` теперь ничего не делает, если состояние не изменилось: раньше каждый world tick снова включал `forcePresent`, сбрасывал DXGI pacing и привязывал Overlay FPS к частоте полного мира;
- DXGI frame-latency permit ожидается ровно один раз и сохраняется до `Present`; результат второго ожидания больше не теряется;
- при лимите, совпадающем с частотой монитора, программный limiter отключается и кадры синхронизирует сам compositor; меньший пользовательский лимит продолжает работать;
- `ShowWindow` вызывается только при реальном включении/выключении, а `SetWindowPos` — только при изменении положения или размера окна ARK;
- нативная проекция `forward/right/up/focal` рассчитывается один раз за кадр, а не заново для каждой из тысяч точек построек и каждой кости;
- исправлен откат динозавров к старой metadata-позиции: сохранение свежего transform теперь учитывает и `Dino`, и `Player`;
- тяжёлый полный обход мира ограничен 50 мс (20 Гц), при этом камера и позиции остаются на 4 мс; это устраняет сотни тысяч временных `ActorRecord` в секунду и связанные stop-the-world GC-паузы на базах с ~5000 объектов;
- скрытое меню больше не пересобирает таблицы на 500 строк и списки племён/структур во время игры;
- диагностика теперь показывает не только последний render, но и его максимум, последний интервал между кадрами и максимальный frame gap за окно 0,5 с. Старое имя `GPU` заменено на корректное `Рендер`, поскольку измеряется полный CPU wall-time `Render + Present`, а не чистое время GPU.

Актуальное значение `RefreshIntervalMs` — `50`; уменьшать его не нужно, потому что оно относится только к discovery/metadata. Плавность уже найденных игроков, динозавров и камеры определяется независимыми быстрыми контурами. Release EXE и native DLL пересобраны вместе, расширенный ABI `ArkOverlay_GetStatsEx` проверен через `--self-test`.

### Второй этап плавности: согласованное движение и batched structures

После аудита выполнен следующий этап, направленный уже на редкие микрофризы, а не только на средний FPS:

- отдельные camera и transform workers объединены в один 4-мс motion loop; камера читается после динамических корней и отправляется вместе с ними;
- добавлен компактный `ArkOverlay_UpdateMotionFrame`: камера и все позиции становятся видимы render thread под одной блокировкой и одной ревизией, поэтому кадр больше не может смешать новую камеру со старой позицией;
- motion loop сканирует полный список из тысяч объектов только при появлении нового world snapshot, а между снимками проходит лишь компактный список игроков/динозавров;
- высокочастотный motion ABI переведён на blittable `ArkNativeMotion` без `float[51]`; массив костей больше не маршалится 200+ раз в секунду;
- camera snapshot переиспользуется, а UI получает согласованную копию scalar-полей под короткой блокировкой; прежние `TrackerSnapshot + List + Dictionary` больше не создаются на каждом 4-мс чтении камеры;
- чтение костей полностью вынесено из 4-мс motion loop в отдельный 16-мс worker и отдельный `ArkOverlay_UpdateSkeletons`; native совмещает прочитанную позу с самым свежим корнем, поэтому медленный skeleton read не задерживает камеру и не откатывает рамку;
- `TrackerSnapshot`, список и `ActorRecord` для быстрых позиций теперь переиспользуются после прогрева;
- чтение скелета использует grow-only thread-local byte buffers, `ExternalTransform` стал value type, а массивы поз кэшируются по адресу игрока;
- кэш `NameResolver` защищён от одновременного чтения/записи actor и skeleton workers;
- native renderer отделил metadata-версию тяжёлого массива подписей от компактной motion-версии; при каждом 200+ Гц пакете больше не копируется весь массив объектов;
- адреса динамических акторов индексируются через hash map вместо линейного поиска по всему native-массиву;
- точки построек основного экрана и мини-радара рисуются через optional `ID2D1SpriteBatch`: тысячи отдельных `SetColor + FillEllipse` заменены на один batch для каждого слоя. При отсутствии Direct2D 1.3 автоматически остаётся старый совместимый путь;
- классификация одинаковых классов построек кэшируется внутри metadata packet и больше не создаёт временную объединённую строку для каждого фундамента;
- диагностика дополнена пиками мира/metadata/позиций/камеры за окно 0,5 с и частотой Gen0 GC. Формат `текущее / пик` специально показывает короткие паузы, которые раньше сразу затирались нулевым следующим циклом.

Release C# и native C++ собраны, полный `--self-test` прошёл. Tracker после сборки запущен на живом `ShooterGame.exe` и успешно открыл read-only handle, нашёл GNames/GWorld и инициализировал DirectComposition overlay. Живая проверка выполнялась уже в сцене примерно с 5100 объектами: процесс отвечал, рабочая память находилась около 95–110 МБ, новых ошибок в логе не появилось. Итоговую плавность и новые пики всё равно нужно подтвердить глазами в насыщенной базе; средние значения теперь менее важны, чем `пик позиции`, `пик кадра` и `GC0/с`.

### Аудит лагов после перехода на WPF (20 августа 2026)

Пользователь сообщил, что подтормаживания в меню начались именно после замены WinForms-интерфейса на WPF dashboard. Найдена и исправлена главная причина в `src/ArkTracker.Reborn/WpfSettingsDashboard.cs`:

Таблицы «Объекты рядом» (страница «Обзор») и «Турели рядом» (страница «Турели») обновляются несколько раз в секунду живыми данными снимка. Старый WinForms `DataGridView` перерисовывает только видимые строки, поэтому `Rows.Clear()` + до 500 `Rows.Add()` был дешёвым. Новая WPF-версия строила таблицу вручную через `StackPanel`: каждое обновление полностью очищало панель и создавало заново до 500 строк × 7 колонок (`Grid` + `TextBlock` без виртуализации) — то есть тысячи новых визуальных элементов и полный layout-проход несколько раз в секунду, пока открыта страница с таблицей. Это и есть тот лаг, которого не было в WinForms.

Добавлен `RowPool` — приватный вложенный класс, который переиспользует уже созданные строки/ячейки между обновлениями и меняет только текст в изменившихся ячейках; лишние строки скрываются через `Visibility.Collapsed`, а не удаляются. `ActorTableCard`, `TurretTableCard`, `RefreshActorTable`, `RefreshTurretTable` переведены на `RowPool`. Заодно у числовых полей, полей цвета и списков ID племён (`NumberCard`, `ColorCard`, `TeamListCard`, `SmallField`) добавлена обработка Enter (снимает фокус и тем самым сразу применяет значение), как уже было у `TextCard` — раньше значение применялось только при потере фокуса кликом в другое место, что ощущалось как не отвечающий на Enter интерфейс.

Полная C# пересборка (`build-reborn.ps1 -SkipNative`, native DLL не менялась) и `--self-test` прошли с кодом `0`; `bin/Reborn/ui-settings.ini` не перезаписывался. Живая проверка плавности меню на игре пользователем ещё не подтверждена.

### Подтормаживание при нажатии на кнопки (20 августа 2026)

Пользователь отдельно сообщил, что клик практически по любой кнопке в WPF-меню ощущается с задержкой. Причина оказалась не в WPF-рендеринге, а в сохранении настроек: `Commit()` в `WpfSettingsDashboard.cs` на каждый клик (тумблер, пункт выпадающего списка, кнопка союз/выбрать и т.д.) вызывает `ApplyWpfSettings()` → `TrySaveSettings()` → `TrackerViewSettings.Save()`, который делал синхронный `File.WriteAllLines` прямо в обработчике клика на UI-потоке — включая сортировку потенциально сотен записей `StructureClassCategories` (ручные назначения класса постройки → категория). На живой базе с тысячами построек эта запись на диск заметно ощущается как лаг при каждом нажатии; раньше в WinForms аналогичного пути «клик → синхронная запись файла» с таким объёмом данных не было.

Исправлено в `ArkTracker.Legacy.cs`: `TrackerViewSettings.Save(path)` разбит на `BuildSaveLines()` (чистое построение текста из настроек, без I/O) и запись. `RadarForm.TrySaveSettings()` теперь строит строки синхронно (это дёшево и обязано остаться на UI-потоке, так как читает живые коллекции настроек), а сам `File.WriteAllLines` уводится в `ThreadPool`; быстрые повторные клики схлопываются в одну ожидающую запись вместо очереди из нескольких. При закрытии окна используется отдельный `SaveSettingsBeforeExit()` — он ждёт короткое время завершения фоновой записи и затем сохраняет синхронно, чтобы последнее состояние гарантированно попало на диск до выхода из процесса.

Сборка и `--self-test` прошли с кодом `0`.

### ESP иногда не прогружается / не появляется заново (20 августа 2026)

Третья жалоба из этой же серии: ESP иногда не появляется как надо. Причина — гонка между двумя независимыми источниками включения/выключения native overlay в `NativeOverlayRenderer` (`ArkTracker.Legacy.cs`):

- `SnapshotPump` в фоновом потоке вызывает `UpdateView(...)` примерно каждые 50 мс независимо от того, открыто ли меню, и внутри всегда выставлял `SetNativeEnabled(requestedEnabled)`, то есть только по переключателю ESP;
- `SetMenuVisible(visible)`, который дергается при открытии/закрытии меню (`ShowInteractiveMenu` / `HideMenuAndReturnToGame`), тоже вызывал `SetNativeEnabled(requestedEnabled)` — параметр `visible` сохранялся в поле `menuVisible`, но **нигде не использовался** для решения о включении.

То есть открытие меню не выключало native overlay по-настоящему (или выключало на мгновение, но следующий фоновый тик `UpdateView` тут же включал обратно), а закрытие меню могло произойти одновременно с фоновым тиком и получить не тот порядок вызовов — из-за этого ESP иногда не появлялся сразу после закрытия меню или продолжал быть виден поверх открытого меню. `menuVisible` был мёртвым полем — записывался, но нигде не читался. То же самое было и в managed GDI+ fallback-рендерере (`UpdateView` там показывал/прятал окно только по `OverlayEnabled`, не учитывая `menuVisible`).

Исправлено: оба места (`UpdateView` и `SetMenuVisible`) в обоих рендерерах теперь считают одно и то же составное условие `requestedEnabled && !menuVisible` (для fallback — `OverlayEnabled && !menuVisible`), поэтому у фонового цикла и у открытия/закрытия меню больше нет возможности отменить решение друг друга.

Сборка и `--self-test` прошли с кодом `0`. Живая проверка (открыть/закрыть меню несколько раз подряд, включая быстрые повторные Insert) пользователем ещё не подтверждена.

### Откат «скрытия ESP при открытом меню» — ESP вообще перестал появляться (20 августа 2026)

После предыдущего фикса пользователь сообщил: меню закрывается нормально, но ESP поверх игры больше не появляется вообще (раньше был просто редкий сбой, стало — не работает совсем). `arktracker.log` на момент жалобы не обновлялся с последнего запуска до этой серии правок, поэтому диагностировать по живому логу не удалось; решение принято по коду.

Вероятная причина: до правки `menuVisible` нигде не читался, поэтому `enabled` в нативном рендерере фактически никогда не переключался — окно overlay оставалось постоянно `enabled=true`, а «исчезновение» ESP при открытом меню было просто визуальным перекрытием поверх него окном меню (`TopMost`). Совмещение `requestedEnabled && !menuVisible` заставило нативную сторону реально проходить цикл `SW_HIDE` → `SW_SHOWNOACTIVATE` при каждом открытии/закрытии меню — а это ровно тот путь (bootstrap-кадр после скрытого DirectComposition target), который уже один раз ломался и чинился раньше (см. «регресс повторного показа ESP» выше). Судя по всему, надёжность этого пути с тех пор не переиспытывалась, потому что до этой правки он никогда реально не срабатывал под WPF-меню.

Так как рисковать нативным DirectComposition/frame-pacing кодом без живого лога и репродукции неразумно, изменение отменено: `NativeOverlayRenderer.UpdateView` и `SetMenuVisible` снова используют только `SetNativeEnabled(requestedEnabled)` — как было до этой серии правок, ESP не выключается по-настоящему при открытом меню, его просто перекрывает окно меню сверху. Поле `menuVisible` оставлено (сохраняется, но не используется) на случай, если позже кто-то захочет отдельно и аккуратно протестировать реальное скрытие/показ overlay-окна. Managed GDI+ fallback-рендерер (используется только если native DLL недоступна, сейчас не активен) свою версию комбинированного условия сохранил — он использует обычный `Form.Show()/Hide()` без DirectComposition/frame-latency, тот же класс регрессии там не воспроизводится.

### «Важные виды существ»: не все дино с полной подписью (24 августа 2026)

Пользователь захотел, чтобы не все динозавры показывали полную подпись (имя/уровень/дистанция/ХП/статус) — например только карно и гига получают детали, а остальные просто точка/рамка без текста. Решили обе озвученные им идеи одним переключаемым механизмом вместо выбора одной:

- **Новая страница-список «Важные виды существ»** на странице «Существа» (`DinoSpeciesListCard` в `WpfSettingsDashboard.cs`) — живой список видов, обнаруженных в игре (тот же паттерн живого обнаружения, что и у классов построек: `knownDinoTypes` в `ArkTracker.Legacy.cs`, наполняется в том же 750-мс цикле, что и `knownStructureTypes`). У каждого вида кнопка «Важный вид».
- Если список пуст — поведение как раньше, у всех дино полная подпись (обратная совместимость).
- Если список не пуст — виды **не из списка** теряют текст подписи (имя, уровень, дистанцию, HP-полосу и текст, статус), но остаются на радаре как точка/рамка — сохраняется пространственная осведомлённость без визуального шума. Выбранные виды показывают всё как раньше.
- Отдельный переключатель **«Показывать только важные виды»** превращает список из «фильтра детализации» в настоящий белый список: остальные виды скрываются полностью, а не просто теряют подпись — это прямой аналог второй идеи пользователя («только карно или гига»).

Реализация: `TrackerViewSettings.PriorityDinoClasses` (`HashSet<string>`, персистится как `PriorityDinoClasses=...`) и `ShowOnlyPriorityDinos` (bool). Белый список — гейт в `TrackerFilter.IsVisible` (и синхронно в диагностическом `VisibilityStatus`). Детализация — новый бит `64` в уже существующем `NativeActor.Flags` (по той же схеме переиспользования битов, что и бит `32` для здоровья ранее в этой сессии): C# считает `dinoShowsDetails` один раз на актёра в `NativeOverlayRenderer.UpdateView` и упаковывает его в `Flags`, а заодно AND-ит в существующий бит здоровья (`32`), чтобы HP-полоса тоже не рисовалась у неважных видов. В native (`ArkOverlayNative.cpp`, `DrawActor`) добавлена одна строка сразу после уже существующей проверки `actor.kind == 2 && (flags & 16) == 0` (та же самая идея — «нет флага показа деталей → return до текста», только для дино вместо построек): `if (actor.kind == 1 && (actor.flags & 64) == 0) return;`. Рамка/точка и её цвет рисуются раньше этой проверки, поэтому не затрагиваются — только текстовый и HP-блок обрезается по return.

ABI не менялось (использован свободный бит существующего `int flags`), но `.cpp` менялся — собирали native и C# полностью (`build-reborn.ps1` без `-SkipNative`) для `bin/Reborn`, затем C# отдельно для `bin/StableCandidate` (`-SkipNative`) с ручным копированием одинаковой `ArkOverlayNative.dll` между папками — то же самое, что и в прошлых native-правках этой сессии (`build-native.ps1` всегда пишет DLL только в `bin/Reborn`). `--self-test` — код `0` в обеих папках.
